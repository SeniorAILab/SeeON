# §3. 스트리밍 윈도잉

> research 문서. 실시간 스트림 입력에서 window 길이 / stride / 지연(latency) 트레이드오프를 정리하고
> 권장 출발점을 제시한다. **단일 "최적값"은 우리 도메인에서 검증된 바 없음**(아래 경고).

## 0. 경고 — "최적 윈도우" 수치를 그대로 믿지 말 것

deep-research에서 **윈도우 관련 주장 6건이 전부 기각**됐다:
| 주장 | 결과 | 출처 |
|------|------|------|
| "3초가 최적" | 0-3 ✗ | [Web: s11036-023-02215-6] |
| "20~25프레임(0.2~0.25s)이 최적, 99.07%" | 0-3 ✗ | [Web: PMC9455026] |
| "1~2초가 최적 트레이드오프" | 0-3 ✗ | [Web: PMC4029702] |

**중요:** 기각 사유 핵심은 (a) 이 수치들이 대부분 **웨어러블 IMU HAR**용이라 **영상에 부적용(wrong modality)**,
(b) 출처가 그 수치를 정확히 뒷받침 못함. → **영상 낙상의 단일 최적 윈도우는 1차 출처로 확정 불가.**

## 1. 코퍼스가 제시하는 출발점 (영상·pose 시계열 기준, within-dataset)

코퍼스의 pose→Transformer 파이프라인 계열이 제시하는 경험적 출발점:
- **윈도우 ≈ 60프레임(≈2초)**, **stride ≈ 15프레임** (≈4 윈도우/초 갱신).
- **~15프레임에서 성능 포화**, **~20프레임 부근 최적 보고**, **최소 ~10프레임 버퍼**.
- pose→Transformer 파이프라인은 76.2 FPS로 실시간 2.5배 여유 보고(연산 측면). [NLM: Real-Time YOLOv11 Pose .pdf]

> 이 값들은 within-dataset 경험칙이며 deep-research가 교차검증하지 못했다. **출발 하이퍼파라미터로만 사용.**

## 2. 트레이드오프 구조 (정성적 — 방향성은 견고)

```
긴 윈도우(예 2~3s)         짧은 윈도우(예 0.5~1s)
+ 시간 맥락 풍부(낙상 전·후 포함)   + 지연 낮음, 빠른 알림
+ 동적(falling)+정적(fallen) 모두 포착  - 맥락 부족 → 일시동작 오탐 위험
- 알림 지연 ↑                    - 짧은 낙상 놓칠 위험
- 자세 변화 누적으로 경계 모호     - 더 많은 라벨 경계 정밀도 요구
```
- **낙상 이벤트 지속시간** 자체가 라벨 경계 정의(§4)와 §2 라벨링에 의존 → **독립 결정 불가**.
- deep-research openQ: "탑다운에서 falling 구간의 시작/끝 정의"가 미해결이므로, **윈도우 길이는
  taxonomy/라벨 경계가 정해진 뒤 자체 데이터에서 튜닝**해야 한다.

## 3. 설계 옵션

| 옵션 | 윈도우/stride | 특성 | 적합 상황 |
|------|----------------|------|-----------|
| **W1. 짧은 슬라이딩(0.5~1s, stride 작음)** | ~15~30f / 5~10f | 저지연 알림 우선 | 빠른 통보가 임상적으로 중요할 때 |
| **W2. 중간(2s/stride 15) — 추천 출발** | ~60f / 15f | 코퍼스 출발값, 맥락+지연 균형 | 일반 출발점 |
| **W3. 긴 윈도우(2~3s+) + 정적상태 확인** | ~60~90f+ | fallen-state 지속 확인으로 오탐↓ | 오탐 비용이 클 때(요양원 알림 피로) |
| **W4. 2단(이벤트 트리거 + 상태 확인)** | 짧은 트리거 → 긴 확인 | falling 감지 후 fallen 지속 검사 | 정밀 알림 |

## 4. 추천 (research 추천 — 결정 아님)

1. **출발값: W2 (60프레임/2초, stride 15).** 코퍼스 경험칙이자 실시간 여유 충분.
2. **단일 최적 신뢰 금지** — 자체 라벨 데이터에서 window∈{15,30,60,90}f를 sweep해 **우리 holdout 기준**으로 선택.
3. 요양원 알림 피로(오탐) 비용이 크면 **W3/W4의 "정적 fallen-state 지속 확인"** 을 가산(§4 taxonomy와 결합).
4. 윈도우 결정은 **taxonomy·라벨 경계 확정 이후**로 순서를 잡을 것(역순 진행 시 재작업).
