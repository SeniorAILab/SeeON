# 침대 탐지(yolo26m) 실측 감사 및 탐지 한계 분석

## 1. 요약

요양원 천장 어안(fisheye) CCTV에서 **다인실 침대 다중 탐지**가 방마다 몇 개까지 잡히는지를 실측했다. 데모와 동일한 `BedDetector`(yolo26m, COCO class 59=bed)를 요양원 `processed` 영상 23개에 직접 돌려 침대 박스를 렌더링·카운트했다.

핵심 결론: **탐지 개수는 전적으로 명시적 코드 파라미터로 결정**되며, 그중 `BED_MAX_DETECTIONS = 4`라는 **인위적 하드 상한**이 가장 강한 한계였다. 23개 중 8개 방이 정확히 4에서 멈췄고, 하드 캡을 제거하자 그중 3개 방이 8~9개로 드러났다(나머지는 실제로 ~4개). 이 캡을 제거하는 것이 가장 크리티컬한 수정이라 판단해 #242로 처리했다. 침대를 bbox 대신 스켈레톤/세그멘테이션으로 표현하는 건은 별도 #243으로 분리했다.

## 2. 방법

- 모델: `ml/models/bed/yolo26m.pt` (#239에서 yolo26n→m 스케일업; nano는 어안 각도 침대를 'couch'/저신뢰로 오분류 → OOD).
- 코드: `core.bed_detector.BedDetector.detect_union(frames)` (프로덕션 경로 그대로).
- 두 가지 측정:
  - **seed**: 첫 8프레임 union — 데모(`live_view.iter_live_frames`)가 화면 초기에 보여주는 값.
  - **ceil**: 영상 전체에서 균등 추출한 10프레임 union — 탐지 상한 근사치.
- 각 방의 대표 프레임에 침대 박스 + `BED i conf`를 렌더링해 시각 확인(몽타주 시트).

## 4. 탐지 개수를 결정하는 파라미터

탐지 "정도"는 아래 명시적 상수로 전적으로 결정된다.

| 파라미터 | 위치 | 값 | 영향 |
|---|---|---|---|
| **`BED_MAX_DETECTIONS`** (제거됨) | `ml/core/yolo_runtime.py` | 4 → **없음** | **인위적 하드 상한**. `dedupe_bed_boxes(...)[:max_beds]`가 NMS/병합 이후 마지막에 강제 절단. 가장 강한 한계였음 → #242로 제거 |
| 가중치 family | `ml/core/bed_detector.py` `BED_WEIGHT_FILENAME` | `yolo26m.pt` | recall의 바닥. nano는 어안 각도 침대 OOD → 미탐(#239에서 m으로 상향) |
| `COCO_BED_CLASS_ID` | `yolo_runtime.py:14` | 59 | class 59(bed)만 카운트. 'couch/chair'로 분류되면 다른 파라미터와 무관하게 영원히 미탐. 휴게실 0개도 이 필터 덕분(정상) |
| `BED_MODEL_CONFIDENCE` | `yolo_runtime.py:15` | 0.25 | 신뢰도 하한. ↑면 흐린 침대 누락, ↓면 더 잡되 오탐↑ |
| `BED_MERGE_IOU_THRESHOLD` | `yolo_runtime.py` | 0.5 | 교차탐지 병합 강도. #239에서 0.2→0.5(낮으면 인접 침대를 하나로 합쳐 과소카운트 — 원래 버그) |
| `BED_NMS_IOU_THRESHOLD` | `yolo_runtime.py` | 0.5 | 프레임 내 중복 제거 |
| `BED_SEED_FRAME_COUNT` | `ml/demo/live_view.py:24` | 8 | (데모) 첫 N프레임 union. 작으면 방 전체를 못 담아 과소카운트(301: seed 1 vs ceil 4) |
| `BED_REDETECT_INTERVAL_FRAMES` + 재탐지 *교체* | `live_view.py:25,129-132` | 30 | (데모) 30프레임마다 **단일프레임 `detect`로 교체**. union이 아니라 교체라 재생 중 침대를 다시 떨굴 수 있음(301-03-27: seed 4→ceil 3) |

## 5. 한계 (정직하게)

- **recall 한계 (근본)**: yolo26m도 COCO 일반 모델이라 어안 왜곡이 심한 각도의 침대를 'couch/chair'로 분류하거나 놓침(404·203-04-19가 1개에 머무는 원인). 완전 해결은 요양원 데이터 파인튜닝.
- **무제한의 대가**: 캡 제거 후 일부 방이 8~9개 → 6인실이라도 9개는 **과탐(over-detection) 일부 포함** 가능성. 단 이는 conf/class/NMS/merge 품질 필터의 몫이지, 인위적 캡으로 가릴 문제가 아님. 캡은 "진짜 침대 수"를 모르게 만들 뿐이었음.
- **데모 시간 샘플링**: seed(8프레임) 과소 + 주기 재탐지 *교체* 로 화면 카운트가 변동. 별도 후속(주기 재탐지를 union 누적으로) 검토 대상이나, 이번 스코프(가장 크리티컬=캡 제거)에서는 제외.

## 6. "침대 스켈레톤" 가능성 (→ #243, 별도 워크트리/PR)

사람은 pose 스켈레톤으로 그려지는데(ADR-025 per-frame 1-pass) 침대도 형상에 맞는 표현이 필요하다는 의견. 어안에서 축정렬 bbox는 침대를 헐겁게 감싼다.

- **세그멘테이션 마스크 — 현재 즉시 가능**: `*-seg` COCO 가중치(class 59=bed)로 침대 픽셀 마스크/윤곽 폴리곤을 렌더. 모델 교체 + 오버레이 추가만으로 됨. 어안 왜곡에 bbox보다 훨씬 잘 맞음. **권장 1순위.**
- **키포인트/스켈레톤 — 커스텀 학습 필요**: "침대 코너 키포인트" 사전학습 가중치는 없음. 침대 코너를 직접 라벨링해 keypoint 모델을 학습해야 함(별도 데이터/라벨 작업).
- per-frame pose 1-pass(ADR-025) 영향 평가 필요(별도 bed-seg 패스 추가 시 빈도/비용). #243에서 다룬다.

> **구현됨 (#243 / ADR-051)**: 세그멘테이션 방식을 채택해 구현 완료 — `yolo26m-seg.pt`(class 59), `BoundingBox.polygon`에 마스크 윤곽을 실어 overlay에서 침대 실루엣 폴리곤을 렌더(bbox는 마스크에서 파생해 bed-exit 판정에 유지). 실측: 502호 8개·202호 4개 전부 폴리곤. literal keypoint "스켈레톤"은 사전학습 가중치가 없어 보류(커스텀 학습 필요).

## 7. 후속

1. (#242, 본 PR) 침대 탐지 하드 상한 제거 — 완료.
